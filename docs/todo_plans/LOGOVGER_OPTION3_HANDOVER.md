## Decision implemented

Tables return typed data. They do not return prose that some runtime
participant must reinterpret, and table-specific game rules are not baked
into engine code.

The contract is:

- `LookupEntry` is abstract and only supplies the lookup band.
- Each lookup table declares one concrete `entry_type`.
- A game pack defines that row type and its required result columns.
- Every `TableEntry` carries one typed root `Outcome`.
- `NoEffect` represents an intentional no-op.
- `OutcomeSequence` represents an ordered, atomic group through typed
  `OutcomeStep` children with contiguous zero-based indices.
- The old generic `LookupEntry.outcome` path is gone. There is no legacy
  fallback.

This phase defines and verifies the data contract. It does not execute
outcomes. Execution policy remains a later phase.

Shelob is the server deployment library. It has no role in rule ingestion,
table lookup, game decisions, or outcome execution. Earlier notes that
assigned it any such role were corrected in the same implementation commit.

## What changed

The engine schema in `schema/packs/rulebook.yaml` now defines the abstract
lookup-row contract, mandatory lookup row type, mandatory table outcomes,
`NoEffect`, `OutcomeSequence`, and `OutcomeStep`. `RollableTable.dice` is
required through class-specific slot usage, without changing the separate
`TaskCheck` contract.

The Cepheus schemas add:

- `CharacteristicModifierEntry` with required printed result columns.
- `DifficultyEntry` with required name and modifier columns.
- `EndCareer` as a game-specific outcome.
- `Currency` as cited vocabulary for money outcomes.

`examples/logovger/seeds/cepheus_book1_tables.json` is the first production
fixture. It includes cited characteristic-modifier rows, law rows, mishap
rows 2 and 3, and injury row 6. Mishap row 3 uses an `OutcomeSequence` for
ending the career and creating a Cr10,000 debt. Injury row 6 points to
`NoEffect`.

The seed verifier now reports semantic violations and rejects:

- Missing, unknown, unrelated, or abstract lookup row types.
- Empty lookup tables.
- Lookup rows whose type does not match the table declaration.
- Empty rollable tables or non-`TableEntry` rollable parts.
- Empty outcome sequences.
- Non-`OutcomeStep` sequence parts.
- Duplicate, gapped, non-zero-starting, or incorrectly ordered indices.

Required scalar fields generated by the vendored C++ generator now receive
value initialization. Making result columns required exposed the previous
indeterminate-state defect. `scripts/test_generate_registry.py` contains the
mechanical regression guard. The broad generated-header diff is the result
of that fix, not handwritten changes to generated code.

## Unresolved design boundary

Sequences solve ordered composition, not player or referee choices. The
schema still needs an explicit choice representation and an authority model
before a choice-bearing rule can be executable. Do not infer that model from
`OutcomeSequence`.

The next hardening phase is outcome execution. Before code changes, present
the executor boundary and choice-authority options to the owner. Do not pick
one silently. The implementation must consume typed outcomes from the KG,
apply them atomically, fail loudly for unhandled concrete outcome types, and
leave rule values in data rather than hard-coding game rules in the engine.
